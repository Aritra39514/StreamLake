1 Project Overview & Goals

StreamLake is a working reference implementation of Confluent's Tableflow product — the capability that continuously materializes Apache Kafka topics into Apache Iceberg tables so that query engines (Spark, Flink, Trino, DuckDB) can read streaming data using standard SQL.

🎯

Core Mission

Bridge the gap between real-time Kafka streams and the analytical lakehouse format (Iceberg/Parquet) — the same problem Confluent Cloud solves at petabyte scale.

⚡

Production Patterns

Every component implements real distributed systems guarantees: at-least-once delivery, idempotent creates, crash recovery, split-brain reconciliation, and supervisor restart.

🏗️

Reference Architecture

Mirrors the Go+Java split Confluent actually uses: Go for the fast, low-memory control plane API; Java for the Kafka+Iceberg data processing path.

🔬

Full Confluent Ecosystem

Kafka (KRaft, no ZooKeeper), Schema Registry, Kafka Connect, ksqlDB, REST Proxy — the complete Confluent stack running locally via Docker Compose.

What problem does it solve?

Kafka is a write-optimised log — perfect for real-time event ingestion, but not queryable by SQL engines without a connector. Iceberg is a read-optimised open table format with ACID transactions, schema evolution, time-travel, and partition pruning — but has no built-in streaming ingest. StreamLake is the bridge: it reads from Kafka, buffers micro-batches, writes atomic Iceberg snapshots, and exposes a REST API for lifecycle management.

Why this matters for Confluent/IBM Tableflow interviews
Every design decision in this codebase maps directly to production Confluent Tableflow: HadoopCatalog → Glue/Unity Catalog swap, at-least-once with Iceberg dedup via kafka_offset, bounded thread pools for worker isolation, split-brain reconciliation between control and data plane, and Kafka Connect as the alternative sink connector pathway.

2 High-Level Architecture

StreamLake is a three-tier system: a Confluent Kafka backbone, a Java data plane that does the heavy I/O work, and a Go control plane that manages lifecycle.

Two-Plane Architecture

StreamLake uses the same Go/Java split as Confluent production:

3 Technology Stack — What, How & Why

Every technology choice is deliberate. Here's the reasoning behind each.

Apache Kafka 3.7 (KRaft mode) Core Backbone

WHAT it is

Kafka is a distributed, append-only commit log. Producers write records to ordered partitions. Consumers read at their own pace using offsets. Records are retained for a configurable time (7 days here), not deleted on consumption.

HOW we use it

The orders topic (3 partitions) receives e-commerce events. Each TableWorker subscribes to one topic and polls in a loop. Offsets are committed after the Iceberg write to guarantee at-least-once delivery.

WHY Kafka specifically

Confluent Tableflow is built on Kafka. Understanding Kafka's partition model, consumer groups, offset management, and rebalance protocol is core to the Tableflow engineering role.

KRaft (no ZooKeeper) — why it matters
Since Kafka 3.3, the Controller Quorum runs inside the broker itself using the Raft consensus protocol. We set KAFKA_PROCESS_ROLES: broker,controller and KAFKA_CONTROLLER_QUORUM_VOTERS: 1@broker:29093. This eliminates the ZooKeeper dependency, reduces operational complexity, and is how Confluent Cloud runs today. ZooKeeper was deprecated and removed entirely in Kafka 4.0.

Apache Iceberg 1.5.2 Table Format

WHAT it is

Iceberg is an open table format for huge analytic datasets. It sits on top of files (Parquet, ORC, Avro) stored in any object store (S3, GCS, ADLS) and adds ACID transactions, schema evolution, hidden partitioning, and time-travel.

HOW it works internally

Every write creates a new snapshot. A snapshot points to a manifest list → manifest files → data files. The metadata.json pointer is atomically updated via rename. No data file is ever modified — only new ones are added. Old snapshots remain intact for time-travel queries.

WHY we chose Iceberg over Delta/Hudi

Confluent Tableflow targets Iceberg specifically. It has the broadest engine support (Spark, Flink, Trino, DuckDB), the cleanest catalog abstraction (swap HadoopCatalog for GlueCatalog with zero code changes), and REST catalog support for cloud-native deployments.

How an Iceberg write works in IcebergTableWriter.java

IcebergTableWriter.java — append()
// Step 1: Write a new Parquet file to the table's data/ directory
String location = table.location() + "/data/" + UUID.randomUUID() + ".parquet";
OutputFile outputFile = table.io().newOutputFile(location);

FileAppender<GenericRecord> appender = Parquet.write(outputFile)
    .schema(table.schema())
    .createWriterFunc(GenericParquetWriter::buildWriter)
    .overwrite()
    .build();

try (appender) { /* write all records */ }

// Step 2: Build a DataFile with column-level statistics (Metrics)
// These stats are what make Iceberg fast — query engines skip whole
// files based on min/max without reading them.
DataFile dataFile = DataFiles.builder(table.spec())
    .withInputFile(table.io().newInputFile(outputFile.location()))
    .withMetrics(appender.metrics())   // ← column stats for pruning
    .build();

// Step 3: Atomic snapshot commit — no existing data is ever touched
table.newAppend()
    .appendFile(dataFile)
    .commit();  // ← writes new JSON snapshot + updates metadata.json pointer

Apache Parquet 1.13.1 Column Format

Parquet is a columnar storage format. Instead of row-by-row storage, it stores all values of a column together. This means:

  • Predicate pushdown: a query like WHERE product_id = 'prod-001' reads only the product_id column, skipping all others.
  • Compression: similar values in a column compress far better than mixed-type rows.
  • Vectorized reads: query engines can read entire column chunks in one SIMD operation.

We added explicit parquet-column and parquet-hadoop dependencies in pom.xml because some Maven mirrors fail to transitively resolve them through Iceberg — a real production build pattern when using SAP's internal Artifactory.

Go 1.22 — Control Plane Lifecycle

WHAT it does

Accepts user REST calls, persists state to SQLite, forwards worker lifecycle commands to the Java data plane, runs a 30-second background reconciler, and exposes Prometheus metrics.

HOW we use Go idioms

Goroutines for parallel enrich() calls with a semaphore (chan struct{}{}) to limit concurrency to 20. Context timeouts (2s per enrichment call). Channels for graceful shutdown signalling.

WHY Go for control planes

Confluent, Stripe, Cloudflare, and LinkedIn all write control-plane services in Go. It starts in milliseconds (critical for k8s readiness probes), uses ~10 MB RAM baseline vs ~200 MB for a JVM service, and the goroutine model maps naturally to "manage N concurrent lightweight tasks".

SQLite with WAL mode State Store

SQLite is the control plane's state database. It stores the mapping between (id, topic, table_name) and live worker status.

Why WAL (Write-Ahead Log) mode?

In default journal mode, writers block all readers. WAL mode allows one writer and many concurrent readers simultaneously. This matters because Go's HTTP handlers run in parallel goroutines — without WAL, a status update would block every concurrent GET /api/v1/tables call.

sqlite.go — DSN with WAL
dsn := path + "?_journal_mode=WAL&_busy_timeout=5000&_foreign_keys=on"
// _busy_timeout: retry for up to 5 seconds before returning SQLITE_BUSY
// _foreign_keys: enforce FK constraints (future extensibility)
conn.SetMaxOpenConns(1) // single connection serialises writes; WAL handles reads

TableWorker — The Core Loop

Each TableWorker is a Runnable submitted to the bounded executor. Its main loop:

1
Guard: check AtomicBoolean before run()

If stop() was called before the executor scheduled this thread, running.get() is already false — the worker exits immediately without opening a Kafka consumer or Iceberg writer. Prevents "zombie" workers that hold resources but were cancelled before they started.

2
Subscribe with ConsumerRebalanceListener

consumer.subscribe(List.of(topic), rebalanceListener) — the listener is called by the broker when partitions are reassigned (scale-out, rolling restart, consumer crash). On revocation: flush the in-memory buffer to Iceberg and commit offsets before partitions are handed to another consumer. This prevents the "lost message window" where records are buffered but not yet committed.

3
Poll loop: accumulate into buffer + pendingOffsets

consumer.poll(300ms) returns up to max.poll.records (500) records. Each record is deserialized from JSON, enriched with kafka_offset and kafka_partition (for deduplication), and added to the in-memory buffer. The highest offset per TopicPartition is tracked in pendingOffsets.

4
Flush when: 100 records buffered OR 5 seconds since last flush

This micro-batching pattern trades latency (up to 5s) for write efficiency (100 records per Parquet file instead of 1). Production Tableflow uses similar configurable batch windows (e.g. 5-minute commit intervals for large tables).

5
flush(): write Iceberg THEN commit Kafka offsets

Order is critical. Writing Iceberg first means: if the JVM crashes after the Iceberg commit but before the Kafka offset commit, the records will be re-delivered and written again (duplicate Iceberg snapshot). This is the at-least-once guarantee. The duplicate can be detected via (kafka_partition, kafka_offset) fields stored in every Parquet row — exactly how Confluent Tableflow handles it.

6
commitSync with exponential backoff on RetriableException

Transient broker errors (leader election, network blip) throw RetriableException. We retry up to 6 times with backoff starting at 1s, doubling to a 30s cap. Non-retriable errors (AuthorizationException) propagate immediately and kill the worker. The watchdog will restart it.

WorkerRegistry — Supervisor Pattern

Every 10 seconds, the watchdog thread scans all workers:

  • status = error: if restart count < 5, call resetForRestart() (sets running=true, clears error) and resubmit to the executor. This handles transient Kafka/Iceberg failures without operator intervention.
  • status = stopped: remove from the ConcurrentHashMap. Frees memory for the Java GC.
TOCTOU race fix — putIfAbsent
A naive implementation uses if (!workers.containsKey(id)) workers.put(id, worker). Under concurrent HTTP requests (two simultaneous POST /workers for the same topic), both threads can pass the containsKey check before either writes — two workers consume the same topic, splitting messages and creating duplicate Iceberg snapshots. putIfAbsent is a single atomic CAS operation that eliminates this race entirely.

Kafka Streams — OrderMetricsStream

Demonstrates two real-world streaming topologies over the same orders topic:

PipelineTopologyOutput TopicUse Case
A — Filter & Forward source → filter(status=PLACED) → sink orders-placed Downstream fulfillment systems only care about new orders
B — Windowed Aggregation source → selectKey(product_id) → groupByKey → 1-min tumbling window → SUM(price) product-revenue-metrics Real-time revenue dashboard; anomaly detection on revenue spikes
selectKey() causes a repartition
The source topic is keyed by customer_id. To aggregate by product_id, we call selectKey((cid, order) → order.getProductId()). Kafka Streams automatically writes an internal repartition topic and re-reads it — guaranteeing all records for the same product land on the same partition before the stateful aggregation. This is the fundamental "shuffle" operation in distributed stream processing.

5 Go Control Plane — Deep Dive

Request Flow: POST /api/v1/tables

handler.go — CreateTable
// 1. Validate input
if req.Topic == "" { writeErr(w, 400, "topic is required"); return }

// 2. Idempotency check — return 409 if topic already registered
if existing, err := h.db.GetByTopic(req.Topic); err == nil {
    writeJSON(w, 409, map[string]any{"error": "topic already registered", "table": existing})
    return
}

// 3. Generate ID, persist to SQLite with status=starting
id := randomID(4)
_ = h.db.Upsert(store.Table{ID: id, Topic: req.Topic, TableName: tableName, Status: "starting"})

// 4. Forward to Java data plane with retry (3 attempts, exponential backoff)
for attempt := 0; attempt < 3; attempt++ {
    resp, err = h.client.Post(h.dataPlaneURL+"/workers", "application/json", bytes.NewReader(payload))
    if err == nil && resp.StatusCode < 500 { break }
    time.Sleep(time.Duration(100*(1<<attempt)) * time.Millisecond) // 100ms, 200ms, 400ms
}

// 5. On success, update SQLite to running; on failure, mark error
_ = h.db.UpdateStatus(id, "running", 0, nil)

Startup Reconciliation — Split-Brain Recovery

When the Go control plane starts, it calls reconcileWorkers():

  • Case 1 — Go restarted while Java kept running: SQLite shows running but Java has the workers already. The reconciler skips these (they're in liveWorkers map).
  • Case 2 — Java restarted, lost its workers: SQLite shows running but the worker is absent from Java's WorkerRegistry. The reconciler re-posts POST /workers to re-register it.
  • Case 3 — Both crashed and restarted: SQLite rows exist, Java has nothing. Full re-registration.
  • Case 4 — Go crashed during worker creation: Java has a worker but no SQLite row. The reconciler sends DELETE /workers/{id} to stop the orphan.

After startup, a background goroutine re-runs this reconciliation every 30 seconds to catch mid-run failures.

ListTables — Parallel Enrichment

handler.go — ListTables (fan-out pattern)
tables, _ := h.db.List()
enriched := make([]store.Table, len(tables))
var wg sync.WaitGroup
sem := make(chan struct{}, 20)  // max 20 concurrent Java calls

for i, t := range tables {
    wg.Add(1)
    go func(i int, t store.Table) {
        defer wg.Done()
        sem <- struct{}{}        // acquire semaphore
        defer func() { <-sem }() // release on exit
        enriched[i] = enrich(ctx, t) // 2s timeout per call to Java
    }(i, t)
}
wg.Wait()
writeJSON(w, 200, enriched)

Without the semaphore, listing 1000 tables would fan out 1000 concurrent HTTP calls to Java. The 20-wide semaphore prevents overwhelming the Java process while still completing in ~(N/20 × 2s) instead of N×2s sequentially.

SQLite State Machine

Worker status transitions are constrained at the database layer by a CHECK constraint:

sqlite.go — DDL
status TEXT NOT NULL DEFAULT 'stopped'
    CHECK (status IN ('starting','running','stopping','stopped','error'))

6 Confluent Ecosystem Components

Schema Registry — Why schemas matter

Without a schema registry, a producer can change a field name and the consumer silently reads null. Schema Registry stores Avro/JSON/Protobuf schemas and enforces compatibility rules (BACKWARD, FORWARD, FULL) on every new version. Our order.avsc defines the canonical Order event schema.

order.avsc
{
  "type": "record",
  "name": "Order",
  "namespace": "com.streamlake",
  "fields": [
    {"name": "order_id",    "type": "string"},
    {"name": "customer_id", "type": ["null","string"], "default": null},
    {"name": "product_id",  "type": ["null","string"], "default": null},
    {"name": "quantity",    "type": ["null","int"],    "default": null},
    {"name": "price",       "type": ["null","double"], "default": null},
    {"name": "status",      "type": ["null","string"], "default": null},
    {"name": "event_time",  "type": ["null","string"], "default": null}
  ]
}

Kafka Connect — Alternative ingestion path

While StreamLake uses a custom Java consumer for maximum control, Kafka Connect provides pre-built connectors for common sources (databases, S3, cloud services). The Confluent Hub has connectors for:

  • Iceberg Sink Connector: directly writes Kafka topics to Iceberg without custom code
  • JDBC Source Connector: CDC from any JDBC database into Kafka
  • S3 Sink Connector: archive Kafka topics to S3/GCS/ADLS as Parquet/Avro

Connect runs on :8083 and is configured via REST API. Workers in the Connect cluster auto-scale by adding more Connect pods in Kubernetes.

ksqlDB — SQL on Kafka

ksqlDB lets you write SQL queries that run continuously over Kafka topics. Example:

ksqlDB query
-- Create a stream from the orders topic
CREATE STREAM orders (
  order_id VARCHAR, customer_id VARCHAR, product_id VARCHAR,
  quantity INT, price DOUBLE, status VARCHAR
) WITH (KAFKA_TOPIC='orders', VALUE_FORMAT='JSON');

-- Real-time revenue per product (last 5 minutes)
SELECT product_id, SUM(price) AS revenue
FROM orders
WINDOW TUMBLING (SIZE 5 MINUTES)
GROUP BY product_id
EMIT CHANGES;

This is the SQL equivalent of our Kafka Streams OrderMetricsStream Pipeline B. ksqlDB uses Kafka Streams internally — it's a higher-level interface for teams without Java expertise.

7 End-to-End Data Flow

Trace a single order event from the producer's keyboard to an Iceberg Parquet file.

1
OrderProducer generates a fake order

A random Order POJO is serialized to JSON: {"order_id":"abc-123","customer_id":"cust-4521","product_id":"prod-003","quantity":2,"price":99.98,"status":"PLACED","event_time":"2026-08-14T..."}. The key is customer_id — guarantees all orders from one customer land on the same partition, preserving per-customer ordering.

2
Producer sends to Kafka with idempotence

enable.idempotence=true means the broker assigns this producer a unique PID (Producer ID) and assigns sequence numbers to each batch. If a network timeout causes a retry, the broker deduplicates the retry using the sequence number — exactly-once delivery to the broker even under retries.

3
Broker appends to partition log

The orders topic has 3 partitions. Kafka assigns a partition based on hash(customer_id) % 3. The record is persisted to the broker's disk under /tmp/kraft-combined-logs/orders-{0,1,2}/. With acks=all, the broker waits for all in-sync replicas (1 here, since single-node) to write before acknowledging to the producer.

4
User creates an Iceberg table via Control Plane API

POST http://localhost:8000/api/v1/tables with body {"topic":"orders","table_name":"orders"}. The Go handler validates, checks for duplicates (409 if exists), persists to SQLite with status=starting, then POSTs to Java: POST http://localhost:9090/workers.

5
Java creates a TableWorker and submits to the executor

WorkerRegistry.start() uses putIfAbsent to atomically register the worker, then submits it to the bounded ThreadPoolExecutor. The worker transitions: starting → running on the first successful poll cycle.

6
TableWorker polls Kafka and buffers records

Each consumer.poll(300ms) call returns up to 500 records from the orders topic. The worker buffers them in-memory and tracks the highest offset per partition in pendingOffsets.

7
Flush: write Parquet file → commit Iceberg snapshot → commit Kafka offsets

When the buffer reaches 100 records or 5 seconds has elapsed: (a) IcebergTableWriter.append(buffer) writes a Parquet file with column stats and commits an atomic Iceberg snapshot. (b) consumer.commitSync(pendingOffsets) advances the consumer group offsets. Any crash between (a) and (b) means re-delivery on restart — duplicate Iceberg snapshot, deduplicable by kafka_offset.

8
Iceberg snapshot is queryable

The Parquet file lands in warehouse/streamlake/orders/data/<uuid>.parquet. The snapshot is recorded in warehouse/streamlake/orders/metadata/. Any Iceberg-compatible engine (Spark, Trino, DuckDB, Flink) can now query: SELECT * FROM orders WHERE status = 'PLACED' using column statistics to skip irrelevant files.

Kafka Streams parallel path

Simultaneously, the Kafka Streams app (make streams) consumes the same orders topic on a different consumer group (streamlake-order-metrics) and produces to two output topics without interfering with the TableWorker path. This is the power of Kafka's consumer group isolation — multiple independent applications can read the same topic at their own pace.

Eight critical distributed systems properties were explicitly implemented. Each was identified by architectural analysis and fixed from first principles.

Code Changes Required for AWS

1. Swap HadoopCatalog → GlueCatalog (one file)

IcebergTableWriter.java — before (local)
import org.apache.iceberg.hadoop.HadoopCatalog;
catalog = new HadoopCatalog(conf, warehousePath);
// warehousePath = "warehouse/"  ← local filesystem
IcebergTableWriter.java — after (AWS)
import org.apache.iceberg.aws.glue.GlueCatalog;
catalog = new GlueCatalog();
catalog.initialize("glue", Map.of(
    CatalogProperties.WAREHOUSE_LOCATION, "s3://my-bucket/warehouse/",
    CatalogProperties.FILE_IO_IMPL, "org.apache.iceberg.aws.s3.S3FileIO"
));
// Everything else — append(), schema, commit — is IDENTICAL

Cost optimization
MSK is the dominant cost. For dev/test, use a single kafka.t3.small broker (~$50/mo) or Confluent Cloud Serverless (pay-per-message, ~$0/mo idle). For production with high throughput, the MSK cost amortizes well vs. self-managed Kafka on EC2.

12 Observability & Monitoring

Key metrics to monitor

MetricSourceAlert thresholdMeaning
Consumer lag (records behind) Kafka broker / MSK > 10,000 records sustained for 5 min Workers can't keep up with producer rate; add worker instances or partitions
records_written counter Java TableWorker Stale (no increase for 10 min while lag > 0) Worker crashed; watchdog should restart; check error status via API
JVM heap usage % Prometheus Java agent > 85% sustained Increase container memory or tune batch size
GC pause time (p99) Prometheus Java agent > 500ms Indicates memory pressure during large batch processing
HTTP error rate (5xx) Go chi middleware > 1% over 5 min Data-plane unreachable or overloaded
Iceberg snapshot commits/min Custom counter in IcebergTableWriter < 1 commit/5 min while lag > 0 Iceberg write path broken; check warehouse path permissions

Accessing metrics locally

# Java data plane metrics (JVM + custom)
curl http://localhost:8001/metrics | grep streamlake

# Go control plane metrics
curl http://localhost:8000/metrics

# Kafka consumer group lag
docker exec broker kafka-consumer-groups \
  --bootstrap-server localhost:9092 \
  --describe --group streamlake-<worker-id>

Log levels

The Java data plane uses Logback (logback.xml). Key log statements to watch:

  • Flushed N records in Xms (total: Y) — healthy write path
  • Rebalance: flushing N records before partition revocation — normal rebalance, no data loss
  • commitSync retriable (attempt N), backing off Xms — transient broker issue, retrying
  • Worker in error state — restarting (attempt N/5) — watchdog triggered, investigate root cause
  • Max restarts (5) reached — giving up — manual intervention required
